# GLM 模型不稳定性研究报告

> 版本：v1 · 2026-08 · 基于本项目历史观测（多次评测/压力测试的实测数据）与代码分析

## 一、结论先行

GLM 的"不稳定"不是单一原因，而是**四类因素叠加**，其中两类我们已经修掉，两类需要平台侧配合：

| 因素 | 表现 | 状态 |
|---|---|---|
| ① 本地并发超限 | 1305"并发数超限"、429 排队 | ✅ 已修复（全局请求信号量） |
| ② 账号余额/资源包耗尽 | 1113"余额不足"（HTTP 429）| ⚠️ 需充值（非代码问题）|
| ③ 平台高峰期排队 | p90 ≈ 24s，偶发 40s+，闪断 | 🔶 平台侧（智谱 2026 算力紧张公告），可用探针量化 |
| ④ 旗舰模型调度不稳 | glm-4.6v（v4 系）实测 0/6 超时；flashx 6/6 稳定 | ✅ 已规避（全模式改用 flashx）|

## 二、历史观测数据（本项目实测）

| 时间/场景 | 现象 | 推断 |
|---|---|---|
| GLM-4.6V 思考链开启 | 单次 40s+，评测 0/6 全部超时 | 旗舰模型高峰期不可用 → 已弃用 |
| glm-4.6v-flashx 稳定对比 | 6/6 成功 @ 平均 10.6s | flash 系调度优先级高、稳定 |
| glm-4v-flash 对比 | 6/6 成功 @ 8.4s | 同上 |
| 高峰期（约 2026-08 多次实测）| 单张分析 13~18s（平时 5~9s）| 平台排队，p90≈24s |
| 100 张压力测试（4 并发请求）| 大量 429/超时，17 分钟才跑完 | **本地并发 4 > 平台 flashx 并发 3** |
| 加全局信号量（并发≤2）后 | 100 张 3 分钟跑完，无超时潮 | 并发超限是主要可修根因 |
| 余额耗尽（code 1113）| 所有请求 0.1s 立即 429 | 账户资源问题，与代码无关 |

## 三、根因分解

### ① 本地并发超限（已修复）⭐ 最关键的代码侧根因
- 平台并发上限：glm-4.6v-flashx=3、glm-4v-flash=1、glm-4.6v=10（并发=同时进行中的请求数）
- 本项目曾出现"2 个任务 × cn 双采样 2 = 4 请求"超限 → 平台 1305/429 → SDK 重试排队 → 超时预算耗尽 → 大量降级
- **修复**：`openai_compat.py` 全局 `Semaphore(2)`，所有请求（分析/复检/工具复核）统一限流，任何组合不超过平台上限，并留 1 余量
- 实测效果：100 张评测从 17 分钟 → 3 分钟，无超时潮

### ② 账号余额/资源包（需用户处理）
- 平台 code **1113**"余额不足或无可用资源包"（HTTP 429 包装）
- 本项目曾因大量评测把额度耗尽，导致"全部请求 0.1s 失败"的假象（被误判为不稳定）
- **已处理**：识别为独立 `BalanceError`，降级并提示"请充值/更换 Key"，不再误报"平台繁忙"
- **建议**：批量评测前先算账（见第五节成本模型）

### ③ 平台高峰期排队（平台侧，可量化）
- 智谱 2026 年多次算力紧张公告，高峰期（白天）明显劣化：p90≈24s，偶发 40s+ 或闪断
- 本项目超时预算 20s 与 p90 24s 相近 → 高峰期约半数请求踩线
- 无法从本地根治；**对策**：① 超时预算 20~25s（已调）② 超时降级链兜底（绝不失败）③ 用户可错峰使用（早晚/深夜明显更稳）

### ④ 模型间调度差异（已规避）
- 同一平台不同模型稳定性差异巨大：旗舰 glm-4.6v（带思考链）高峰期基本不可用；flash 系稳定
- 本项目已全模式统一 flashx（放弃 glm-4.6v 思考链），稳定性实测 6/6

## 四、已落地的稳定性工程

| 措施 | 说明 |
|---|---|
| 全局请求信号量（并发≤2）| 从根上杜绝并发超限（1305/429 排队）|
| 超时预算分级（fast/balanced 20s、deep 25s）| 与平台 p90 匹配，减少无谓降级 |
| SDK max_retries 2→1 | 429/余额不足快速失败走降级链，省重试等待 |
| 错误分类（1301 审核 / 1305+429 繁忙 / 1113 余额）| 降级信息准确，用户能对症处理 |
| 降级链（超时→先验/检索→固定兜底）| 任何平台故障都保证"有结果" |
| 全模式 flashx | 避开旗舰模型的不稳调度 |
| 自适应采样（cn 模式）| 结论充分只调 1 次，减少平台压力与费用 |

## 五、验证与建议

**探针脚本**：`scripts/probe_glm.py`（充值后可跑，用数据说话）
```bash
python -m scripts.probe_glm --calls 20 --model glm-4.6v-flashx --concurrency 2
# 建议：白天高峰、晚上、深夜各跑一轮对比
```

**判断标准**：p90 >15s 且失败率 >10% → 平台高峰期；失败码 1113 → 余额；1305 → 并发（本地信号量应已杜绝）。

**剩余建议（平台侧/长期）**：
1. 余额监控：设置页显示"当前 Key 余额"提示（智谱无公开余额 API，需手动查）——低成本：在结果页余额不足时已提示
2. 多平台冗余：设置页已支持多 Key 一键切换——智谱高峰时可切通义/豆包（已支持）
3. 错峰使用：高峰期（白天）尽量用 fast 模式（图更小、更快）

## 六、成本模型（为什么"贵"）

- GLM-4.6V-FlashX 单价约 ¥0.6/百万 tokens（图片 token 大：1024px 图 ≈ 数百~上千 token）
- 本项目一次评测 ≈ 100 张 × 双采样 ≈ 200 次调用 ≈ 数元~十几元
- **省钱**：评测用单采样（`samples=1`）+ fast 模式（768px 图小一半 token）；平时用自适应采样（多数图只调 1 次）
- 新版设置页可切低价平台（豆包/硅基流动等），自由选择
