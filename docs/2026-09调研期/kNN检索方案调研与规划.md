# kNN 检索方案调研与规划

> 日期：2026-09-14
> 背景：bench_hard 51.6% Top-1，15 张错图中 13 张正确国家不在 CLIP Top-10
> 目标：突破51.6%，至少提升到56%+

---

## 一、为什么分类到顶了，检索还有空间

### 分类的天花板

当前系统用 CLIP 做零样本分类：101 国 × 3 template = 300 个文本向量，与图片向量做点积。

问题：
- 文本描述是**抽象概括**（"a street view photo taken in Austria"），无法捕捉具体场景
- 荒野图（71%）没有文化标记，CLIP 只能靠植被/地形判断，而这些特征在多个国家间高度重叠
- 101 个固定类别 = 101 个"桶"，分类器被迫把每张图塞进其中一个桶

### kNN 的优势

kNN 不分类，改为**检索**：
- 参考图是**具体实例**（真实的玻利维亚乡村照片），比文本描述精确得多
- 无固定类别限制——相似就是相似，不需要"玻利维亚"这个文本标签
- 荒野图虽然 CLIP 文本匹配差，但**图片相似度**可能找到正确的参考图

### 关键证据

| 系统 | 方法 | bench_hard/OSV-5M 国家准确率 |
|---|---|---|
| 我们（StreetCLIP zero-shot） | 300 文本向量分类 | 51.6%（bench_hard） |
| OSV-5M baseline | 5M 训练图线性探针 | **68%**（OSV-5M test） |
| GeoGuessr 选手 | 参考图检索 + 经验 | 80%+（公开数据） |

OSV-5M baseline 用 5M 训练图做线性探针就达到 68%，说明**给模型足够的参考信息**确实能提升。kNN 是比线性探针更灵活的检索方式，理论上能达到更高。

## 二、kNN 方案设计

### 2.1 架构

```
新图片
  │
  ├─ StreetCLIP 编码 → 768 维向量 ─┐
  │                                  │
  ├─ OCR 语系快筛（可选）───────────┤
  │                                  ▼
  │                        FAISS 检索（余弦相似度）
  │                                  │
  │                          k 个最近邻（已知标签）
  │                                  │
  ├─ 投票：国家（k=5~10）───────────┘
  │
  └─ Top-1 国家内，再检索城市 → 坐标
```

### 2.2 关键参数

| 参数 | 建议值 | 理由 |
|---|---|---|
| 编码模型 | StreetCLIP ViT-L/14@336 | 与当前系统一致，无需额外模型 |
| 图库规模 | 5000~20000 张 | 太小覆盖不足，太大检索慢（但 FAISS <1ms） |
| k 值 | 5~10 | 太小噪声大，太大引入不相关图 |
| 距离阈值 | cosine > 0.25 才投票 | 低于阈值说明没有足够相似的参考图 |
| 索引方式 | FAISS flat（暴力搜索） | 20000 × 768 × 4B ≈ 60MB，暴力搜索 <1ms |
| 标签粒度 | 国家 + 城市 | 先投国家，再在 Top-1 国家内投城市 |

### 2.3 与现有系统的融合策略

**不要替换 StreetCLIP 分类，而是并行运行、加权融合：**

```
StreetCLIP 分数（101 国零样本）  ─┐
                                  ├─ 加权融合 → 最终 Top-3
kNN 检索分数（参考图投票）      ─┘
```

- 当 kNN 置信度高（Top-1 票数 > 60%）且与 CLIP 一致 → 高置信
- 当 kNN 与 CLIP 不一致 → 取 kNN（因为 kNN 有真实图片佐证）
- 当 kNN 置信度低（票数分散）→ 取 CLIP（退化到当前系统）

## 三、数据源评估（国内可达性）

### 3.1 OSV-5M（最佳候选，但太大）

| 项 | 值 |
|---|---|
| 规模 | 500 万张 Google Street View 图片 |
| 标签 | GPS 坐标（可映射到国家/城市） |
| 格式 | 图片 zip（258 GB）或 WebDataset tar（345 GB） |
| 许可 | MIT |
| 国内可达 | ⚠️ HuggingFace 需镜像（hf-mirror.com），图片本身在 Google CDN（可能被墙） |
| 子集 | `mkartofel/osv5m-ch-subset` 仅1.9 GB（瑞士，太小） |

**关键问题**：OSV-5M 的图片存储在 Google Street View CDN，国内可能无法直接下载。需要验证。

### 3.2 Netryx Hub（已验证可用，但覆盖窄）

| 项 | 值 |
|---|---|
| 已验证 | 莫斯科、纽约、曼哈顿索引可下载 |
| 格式 | 预计算的 MegaLoc 描述符（不是原始图片） |
| 问题 | 只覆盖少数城市，无荒野覆盖 |

### 3.3 替代方案：自建参考图库

| 数据源 | 可达性 | 适合度 | 说明 |
|---|---|---|---|
| **iNaturalist API** | ✅ | ❌ | 自然照片≠街景，特征空间不同 |
| **Bing Maps 街景** | ❓ 未测试 | ⚠️ | 国内可能可达，需 API Key |
| **Wikimedia Commons** | ✅ | ⚠️ | 有地理标签的风景照，但非街景 |
| **自己收集** | ✅ | ⚠️ | 费时但质量可控 |
| **OSV-5M 子集下载** | ⚠️ 需验证 | ✅ | 如果 Google CDN 可达，选择性下载 10000 张 |

## 四、实施路线图

### Phase 1：数据获取（1-2 天）

1. **验证 OSV-5M 图片在国内的可达性**
   - 尝试下载 osv5m/osv5m 的1个 test zip（最小的）
   - 如果 Google CDN 被墙，走代理或放弃
   - 如果可达，下载 test 集（约 50GB）并提取 10000 张代表性样本

2. **如果 OSV-5M 不可达，启动自建图库**
   - 从 bench50 + bench_hard（85 张已知标签）开始
   - 用 CLIP 编码并建立 FAISS 索引
   - 逐步从 Bing Maps / Wikimedia / 手动收集扩充

### Phase 2：kNN 引擎实现（1-2 天）

3. **实现 FAISS 索引**
   - `backend/app/retrieval/knn_index.py`
   - StreetCLIP 编码 → FAISS flat 索引
   - 查询接口：`knn_search(image_bytes, k=5) → [(country, city, score, lat, lon)]`

4. **与 orchestrator 集成**
   - 并行运行 StreetCLIP 分类 + kNN 检索
   - 加权融合逻辑

### Phase 3：评测与调优（1 天）

5. **在 bench_hard 上评测**
   - kNN 单独的准确率
   - kNN + CLIP 融合的准确率
   - 调优 k 值、距离阈值、融合权重

### Phase 4：扩展图库（持续）

6. **从评测结果中学习**
   - 对 kNN 错误的图，分析原因（参考图不够？距离太远？）
   - 针对性补充参考图

## 五、风险与备选

| 风险 | 应对 |
|---|---|
| OSV-5M 国内不可达 | 自建小图库 + Bing Maps API |
| kNN 对荒野图无效 | 接受荒野只给大区级，城市图保持精度 |
| FAISS 内存占用 | 20000 图 × 768 维 × 4B = 60MB，可接受 |
| 参考图覆盖不足 | 优先覆盖 bench_hard 的 19 个国家 |
