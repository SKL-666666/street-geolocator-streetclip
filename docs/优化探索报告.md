# 街景定位工具 — 优化探索报告

> 基于对代码库的完整盘点（管线/前端/评测/测试全部在握）与已量化的现状指标。
> 分类标准：**收益 × 可行性 / 成本**，全部方案不新增付费服务（延续"免费优先"原则）。

---

## 一、现状全景（已验证事实）

| 维度 | 现状 |
|---|---|
| 精度 | 国家 Top-1 ≈ 45%（23 张真值图集，GLM-4.6v）；KB 证据覆盖 100% |
| 速度 | 平衡模式平均 ~10s（6 张实测最大 13s）；快速 ~8s；深度 13~60s |
| 能力 | 3 模式 / EXIF 快路径 / Geo-KB 证据矩阵 / MixVPR 先验 / 工具查证 / KartaView 街景 / 缓存 / 批量 / 候选列表飞图 / 高德地图 |
| 测试 | 45/45；评估脚本支持消融与历史对比 |
| 已知短板 | 见下"二、剩余短板" |

## 二、剩余短板盘点（诚实清单）

1. **LLM 复检环节未接线**：`VERIFY_PROMPT`（Prompt B）已写好但从未调用——原计划"候选街景图 + 查询图拼图送 LLM 判定同地"的最后裁决缺失。候选只到"相似"，没有"确认"。
2. **城市假设坐标表太小**（~50 城）：LLM 提出的大多数城市不在表内 → 候选降级到先验/国家级，丢失信息。
3. **城市名无中文映射**：先验/地理编码候选显示英文城市名（Budapest），与"国家名中文"体验不一致。
4. **评测集与先验画廊同源**（都来自 AI_GeoDetect）：MixVPR 的独立精度从未被真实验证。
5. **GLM 单次线索提取波动**：同一张图两次运行，语言/驾驶侧有时漏提 → KB 命中不稳定（单次采样方差）。
6. **EXIF 快路径无城市名**：有坐标但不知道"这是哪座城"（无本地最近城市解析）。
7. **EXIF 时间未利用**：拍摄时间 + 时区 + 场景光照可做太阳方位交叉验证（GeoGuessr 核心技巧之一）。
8. **深度模式不够"深"**：只是开思考链+大图，没有多轮迭代（假设→检索→复检循环）。
9. **tasks.json 无限增长**：无 TTL/上限管理；缓存无手动清理入口。
10. **wiki 实体过滤器仍漏描述句**（"绿色金属围栏"类仍会被查询）。
11. **kartaview 候选缺城市名**：街景点 city 为空，显示"候选点"（可继承上级候选城市）。
12. **结果无导出**：GeoJSON/KML/CSV 未实现；无历史页 UI（API 已有）。
13. **批处理顺序上传**：多图时逐张排队，无并发度控制（受限于 LLM 限流，可适度并行 2~3）。
14. **置信度未校准**：final_score 与真实命中率的关系未统计（评估集可算校准曲线）。
15. **脚本控制台中文乱码**（GBK）：纯展示问题，脚本输出建议强制 UTF-8。

## 三、优化方案库

### 🟢 第一档：高价值 × 低成本（每项 ≤2 天，几乎全免费）

| # | 方案 | 做法 | 收益 |
|---|---|---|---|
| A1 | **LLM 复检闭环接线** | 把 KartaView 拉到的候选街景图与查询图拼图，调用 VERIFY_PROMPT 让 LLM 判定"是否同一地点"，确认者置顶、否决者降权 | 候选从"相似"变"确认"，街道级可信度质变；Prompt 已写好，只差接线 |
| A2 | **城市中文名映射** | 内置 ~200 城 中/英对照表，先验/地理编码候选统一显示中文 | 体验一致性（当前 Budapest 英文） |
| A3 | **城市坐标表扩充**（~50→500） | 数据录入（主要国家大中城市），LLM 城市假设更多能落点 | 城市级候选命中率显著提升，减少降级 |
| A4 | **独立评测集（KartaView 采样）** | KartaView 免 key 拉取 3~5 城真实街景建独立测试集（与画廊不同城），重跑评测 | **MixVPR 独立精度首次被真实验证**，评估数字变可信 |
| A5 | **EXIF 快路径补城市名** | 本地最近城市表（500 城坐标 → 最近邻），秒级返回"巴黎·埃菲尔附近" | 快路径 UX 升级 |
| A6 | **双次采样合并**（快速模式） | 同图跑 2 次线索提取取并集（flash 模型便宜快） | KB 命中率提升（单次方差减半） |
| A7 | **置信度校准曲线** | evaluate.py 统计 final_score 分档命中率，输出阈值建议 | 阈值有据可依（">0.6 才显示城市级"） |
| A8 | **候选城市名继承** | kartaview/streetview 候选 city 为空时继承主候选城市名 | 列表显示完整 |

### 🟡 第二档：中等成本（3~7 天，核心杠杆）

| # | 方案 | 做法 | 收益 |
|---|---|---|---|
| B1 | **FAISS 街景索引（Phase 2 主线）** | KartaView/Mapillary 数据管线 + MixVPR 描述子建城市库（每城 1~5 万张，CPU 可建）+ 检索→复检闭环 | **街道级定位落地**（最大精度杠杆，积木已全部就位） |
| B2 | **深度模式多轮迭代** | 深度模式跑 2 轮：首轮假设 → 检索/回查 → 拼图复检 → 修正假设再验 | 深度模式名副其实 |
| B3 | **时区 + 太阳方位交叉验证** | EXIF 时间 + 候选时区 + 场景阴影方向/长度（LLM 输出）→ 校验候选 | 排除性证据（错误候选被时间矛盾否决） |
| B4 | **批处理并发 2~3** | 批量上传时受控并发（asyncio 信号量），单张速度不变、整体吞吐提升 | 批量体验 |
| B5 | **结果导出 + 历史页** | GeoJSON/KML/CSV 导出 API + 前端历史列表页（API 已有） | OSINT 工作流闭环 |
| B6 | **缓存治理** | tasks.json TTL（30 天）+ 上限（500 条）+ 清理按钮 | 长期运行不膨胀 |

### 🔵 第三档：长期/大成本（2 周+）

| # | 方案 | 做法 | 收益 |
|---|---|---|---|
| C1 | **自训城市分类器** | AI_GeoDetect 方法论（H3 防泄漏 + 对比实验）微调轻量模型，城市 Top-1 目标 85%+ | 本地零成本快速通道（评测显示专用模型 89.4% vs 通用 LLM） |
| C2 | **多图联合定位** | 同一地点多张照片一起上传 → 候选交集收缩 | 精度 +1 档 |
| C3 | **全景图支持** | 360°/鱼眼展开（KartaView 全景序列） | 线索量翻倍 |
| C4 | **地图热力图** | 候选点不确定性热区可视化（多候选时） | 决策辅助 |

## 四、推荐路线图

```
第 1 步（~1 周，免费）→ A 档全做：复检闭环 + 城市中文名 + 城市表扩充 + 独立评测集
   里程碑：MixVPR 独立精度有数字；候选带"已确认/待确认"标记
第 2 步（~1 周）→ B1 FAISS 索引（Phase 2）：街道级
第 3 步（持续）→ B2/B3/B5 + C 档按需
```

**优先级论证**：A1（复检闭环）是"代码已写好、只差接线"的最大浪费点，收益立现；
A4（独立评测集）解决当前最大的可信度漏洞；B1 是唯一能改变"45% 天花板"的路线。

## 五、决策

- 全部方案**零新增付费**（KartaView 免 key、Natural Earth/OSM 免费、本地 CPU）。
- 需要你拍板的取舍：A1 复检会加 1 次 LLM 调用（+2~4s，平衡模式）；B1 建库需磁盘
  （每城 0.5~2GB）与数小时 CPU 构建时间。
